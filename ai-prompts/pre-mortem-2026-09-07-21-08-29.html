Executive Summary

The biggest risks in this tree cluster around trust boundaries and release gates. The launcher still contains remote-bootstrap messaging and a live self-install path, while scheduled runs for authenticated providers do not carry a durable secret strategy. On the quality side, the current PowerShell acceptance suite is already red, and the repository has visible Python tests that are not included in the automated gate. The provider verifier also misses Python sources, so the main non-Node surface is not covered by the direct-AI-interface policy.

In short, the repository has useful hardening work in place, but the remaining gaps are concentrated where they can do real damage: unattended runs, secret handling, bootstrap trust, and test coverage. Several of the findings below are testable assumptions where the code strongly suggests a risk, but a follow-up agent should confirm the runtime behavior before treating them as proven defects.

Core Critical

Scheduled authenticated runs are not self-contained

The launcher can accept a provider API key at run time, but the scheduled task path does not persist that secret or create an equivalent secure credential reference. That means the task can start successfully once and still fail on later triggers when the current process state is gone.

Priority

Severity

Likelihood

Impacted area
Authentication, scheduled automation

Failure mode

A user can register a task for OpenAI, Anthropic, or Azure and watch the immediate run work, but the later Task Scheduler run has no durable path back to the API key. The Azure endpoint and deployment also ride on mutable defaults, so the scheduled task does not have a frozen provider context.

Evidence or rationale

  • scripts/launch.ps1:1339-1348 sets the provider key only in the current process environment.
  • scripts/launch.ps1:2203-2222 saves and loads defaults without persisting ApiKey.
  • scripts/launch.ps1:1815-1864 builds the task plan without a credential store or secret snapshot.
  • README.md:38-39 explicitly says API keys are never persisted to launch.json.

Why this matters

Scheduled runs that depend on paid or authenticated providers can quietly break after registration. The user sees a successful registration flow but later gets a dead task, which is a high-trust failure for unattended automation.

Recommended mitigation

Either persist a secure credential reference that the task can reopen at runtime, or gate scheduled registration for authenticated providers until a safe secret store is available. Keep Ollama unchanged, because that path does not need a secret.

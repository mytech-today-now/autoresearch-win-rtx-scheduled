5. Checkpoint saves only every 60 seconds

The training loop is still wall-clock checkpointed, so an abrupt exit can discard nearly a minute of work even in a short five-minute run.

Title

Checkpoint saves only every 60 seconds.

Kind

Core.

Priority

5.

Severity

Medium.

Likelihood

Possible.

Impacted area

Recovery and progress retention.

Evidence or rationale

train.py:958-961 defines CHECKPOINT_SAVE_INTERVAL_SECONDS = 60.0. The training loop uses that interval in train.py:1496-1516 to decide when to write a periodic checkpoint, which means a crash can erase the work done since the last time-based save.

Failure mode

If the process is killed, the last 60 seconds of progress may not exist anywhere except GPU memory and ephemeral process state. On a five-minute run budget, that is a large share of the total experiment.

Why this matters

Long checkpoint gaps make crash recovery feel random and expensive. They also make it harder to compare failed runs, because the last saved state may be far behind the point where the actual failure happened.

Recommended mitigation

Reduce the interval, add a step-based trigger, or save more aggressively when the run is near its deadline. Keep the final clean-exit save and the checkpoint format stable.

Keep the final save on clean exit and the resume format unchanged. Add a regression test that proves the loop saves at the new cadence and still writes a final checkpoint. Baseline tests should still verify that resume-from-checkpoint works after the cadence change. Document the maximum expected loss window after a crash.

Regression tests

  • A short run still emits a checkpoint at the intended new cadence.
  • The final save still happens when the run ends cleanly.

Additional baseline tests

  • Resume from an existing checkpoint still works after the cadence change.
